All times below are Pacific unless marked UTC. Scope is regular Favorites in DEMO, its dashboard, and shared infrastructure required to preserve its observations and operation. Traceability is through PR #365, the Render Deploys and Events views, and the Cloudflare Worker metrics and monitor pages.

## Findings and fixes

- **Backup scans:** The multipart query used a collation-sensitive indexed range without a literal prefix predicate. `demo/shadow/bot-performance-history/` and related keys can sort inside the `demo/shadow/bot/` range and feed minute-by-minute history back into each mutable-control backup. Apply `starts_with` to the bounded SQL scan and the matching audit census. The existing upper-tail guard, consistent transaction, R2 full readback, previous receipts and source history remain in place. The disposable PostgreSQL regression puts a neighboring history row inside a widened range and verifies that both backup modes under test capture only the declared namespace and leave the history row in PostgreSQL. Render's external DB route is private. Compare the next successful backup's scope count and verify its root through the existing receipt process before concluding this accounts for the entire spike.
- **Market discovery and fees:** The 30-second series/event metadata and 60-second per-market feed authorization checks already refuse stale entries, but the raw rows and three sets of per-key locks could outlive their markets indefinitely. Evict expired values and release locks as soon as their last active caller or waiter exits. No additional fee requests are issued by expiry itself. Same-series and same-event requests still share verified reads, and zero-maker-fee checks still cover the whole eligibility interval.
- **Market data and engines:** PR #285 already bounded print deduplication to the valid replay overlap, and PR #259 removed redundant evidence aggregation. Both are ancestors of the observed staging revision. There is one shared feed. Existing idle/paused engine checks skip hot book and clock fan-out except for exposure and finalization. Existing expiry maintenance releases closed depth, keeps unsettled positions and moves completed accounting to durable aggregates. There is no evidence that pending settlement caused the November 27 sampled peak. PR #247 overlaps subscription fan-out, PR #124 overlaps checkpoint scheduling, PR #125 overlaps fee refresh and PR #157 overlaps diagnostic batching. None was merged by this audit. The open PRs #361, #363 and #364 own trading discovery changes and remain separate.
- **Repeated state and database work:** Release the old derived dashboard snapshot at publication completion so it cannot coexist with the next full build. Financial checkpoints, status precision and the existing report cadence are preserved. Sample cgroup charge, anonymous memory and file cache alongside process RSS at the existing pipeline log cadence. These measurements distinguish the next backup/cgroup spike from long-term process retention. No changes to archived records, worker roles, subscriptions, instance plans or admission thresholds.
- **Cloudflare:** Keep the existing origin-authenticated workspace stream and extend its bounded, byte-preserving strategy to the regular Favorites folder research response. The API publishes a route-specific contract marker after constructing the existing validated shape. Older API versions continue through the existing gateway validation, and other routes cannot opt in using this marker. Pause automatic dashboard polling in hidden tabs and refresh as soon as the tab becomes visible. Observability on the staging Worker enables invocation logs and keeps traces disabled. Cloudflare runs the gateway and static UI. Render continues to own authenticated database reads, settlement and paper execution.

## Verification and alert ownership

- The source checkout is based on deployed processing revision `0fdfee5`. PR #365 stages the changes on `build/google-auth-foundation` after API/PostgreSQL and one-contract Favorites checks. Confirm Render worker and API revisions independently. The staging Cloudflare workflow checks the published asset bytes against the release commit. Keep all real-order and parked-strategy controls in place.
- `tools/favorites_worker_alerts.py` is an independent evaluator. It uses separate Render event, memory and operational log evidence, with a one-hour minimum event lookback and 15 minutes of overlap after the last complete poll, deduplication by event ID, and no advance for failed event pages. A sampled memory incident escalates at 90% and 95%, or after 30 minutes above 75%. It flags a missing worker heartbeat, a persistent discovery break, stale books for active markets, overdue regular Favorites settlements, and sustained low submissions or fill activity with available evidence. One live read-only evaluation caught tier-two memory pressure and a 29-minute discovery interruption. The recurring Render check is a local Codex heartbeat every ten minutes, independent of the Render worker process. Local scheduling depends on the Codex host being available.
- The pre-existing Favorites Worker Alerts chat reports only the processing worker and activated after the crash burst. Its newer “zero new crashes” messages agree with the checked event history. Its threshold-crossing-only summaries can remain quiet for many hours during an open incident. The new heartbeat covers the escalation and crash signals. Review or retire the older schedule from its own chat if duplicate notices become noisy.
- Cloudflare's enabled native monitor **Money Tree staging Worker CPU limit** checks `events.workersInvocations` for `scriptName = 'pocket-analytics-staging'` and `status = 'exceededCpu'` every minute and emails the account owner. It is independent of Render and does not require deployment of the code changes. For automated reads from outside Cloudflare, use Workers Metadata Read-Only scoped to staging plus Account Analytics Read for the account-scoped Analytics SQL API. The active dashboard session was sufficient for the audit and native monitor. Report request route and `invocationType` from new invocation logs when available. No historical logs can be recovered for intervals with logging disabled.
- A local Node replay exercised 40 requests through each path against the same 1,085,889-byte load of 75 synthetic Favorites bots and checked a SHA-256 digest on every response. Mean local process CPU was 12.13 ms on the old parse path and 2.35 ms on the streaming path. Local measurements include Node stream handling and are not Cloudflare runtime quantiles. A production edge comparison still requires post-release metrics, comparable dashboard traffic and route-level evidence.

## Acceptance still to verify

Compare equal pre/post market windows and at least one overnight period and scheduled backup cycle. Require sustained memory below 70%, measured peak headroom, new Render crash count, regular discovery admissions and fresh books, attempt and actual fill counts, overdue versus vendor-pending settlements, and independent historical outcome/statistical agreement. Require the native Cloudflare monitor to continue running, route attribution for residual failures, and zero CPU-limit outcomes under comparable normal load. A successful short release or synthetic replay does not certify that sustained targets are met.
